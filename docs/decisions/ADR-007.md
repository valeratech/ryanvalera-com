# ADR-007 — Dual-Origin Restoration (October 2026)

## Status

Accepted

## Date

October 2026

---

## Context

In September 2026 the GitHub Pages origin lost its certificate. GitHub issues and renews a Pages certificate through the site's custom domain, and the custom domain was `ryanvalera.com`, a proxied hostname behind the Cloudflare Load Balancer, so renewal could not complete. The certificate expired on 2026-09-17. Because the Load Balancer's health monitor verifies origin certificates, the `github-pages-primary` pool went Critical, and Cloudflare Pages served production alone, with no healthy standby. That degraded state was accepted for a time and then superseded by the Owner on 2026-10-05, which opened the restoration recorded here.

In the same configuration, `pages.ryanvalera.com`, the secondary origin's hostname, was proxied, so load-balanced requests passed through the zone's edge processing twice, and `www.ryanvalera.com` was still the June 2026 proxied `CNAME` to `valeratech.github.io`.

## Decision

The October 2026 repository audit restored both origins with these changes:

- **D1 — a separate DNS-only custom domain for GitHub Pages.** `gh.ryanvalera.com` is a DNS-only `CNAME` to `valeratech.github.io` and GitHub Pages' custom domain; `ryanvalera.com` is verified for GitHub Pages at the account level, and the verification record is retained. The Load Balancer's GitHub endpoint keeps the address `valeratech.github.io` and, since 2026-10-08, sends `Host: gh.ryanvalera.com`.
- **D2 — `www` redirected at the edge.** `www.ryanvalera.com` is a proxied, redirect-only record, and a zone Redirect Rule answers it with a `301` to the apex.
- **C3 — a DNS-only custom domain for Cloudflare Pages.** `pages.ryanvalera.com` is DNS only; the Load Balancer's secondary endpoint and its Host header stay `pages.ryanvalera.com`.
- The pool order is unchanged: GitHub Pages primary, Cloudflare Pages secondary.
- **D4 — the automated purge retired.** The `deploy-and-purge.yml` workflow was removed on 2026-10-10. The deletion of its three repository secrets and of the expired Cloudflare token it used is a separate, governed step.
- Every page carries a canonical link to its extensionless apex URL, and the repository `CNAME` file, which GitHub ignores under the Actions publishing source, was removed (2026-10-10).

## Rationale

- While its custom domain is proxied, GitHub cannot issue or renew the certificate, and the Load Balancer's certificate check then fails. A DNS-only hostname lets GitHub issue the certificate again.
- A DNS-only secondary hostname removes the second pass through the zone's edge processing.
- The purge workflow could no longer work as designed: its `page_build` trigger could not fire under the Actions publishing source, and its last runs failed authentication.
- The canonical form is the URL form that both origins answer directly with `200`.

## Consequences

- Both pools are Healthy again: GitHub Pages primary serving, Cloudflare Pages secondary on standby.
- Two origin hostnames, `gh.ryanvalera.com` and `pages.ryanvalera.com`, are independently reachable and serve the site directly, without the Cloudflare edge controls. ADR-006's premise that no uncontrolled direct-serve path remains is therefore superseded, while its canonical-origin policy stands; ADR-006 itself is left unchanged as a July 2026 record.
- The project URL `valeratech.github.io/ryanvalera-com/` now redirects to `https://gh.ryanvalera.com/` rather than to the apex.
- Each origin certificate needs its own renewal check: going by its scope, the Universal SSL alert covers the edge certificate only (`docs/runbooks/notifications.md`).
- No purge runs on deployment, so on the paths the HTML cache rule covers (`/` and the `.html` pages) an updated page can still be served from the edge cache after a deployment unless a manual purge is made (`docs/cache-governance.md`).
- Failover between the origins is designed behaviour; a controlled failover proof of the restored configuration is pending.
